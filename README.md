# Bouvane company website

A Django site for Bouvane's application-aware security platform. Includes AIWAF,
Bouvane Cloud beta signup, and a contact form. Original CSS takes inspiration
from PyCon and DjangoCon's conference design language using the supplied logo's
red, orange, and gold palette; no third-party conference stylesheets are copied.

## Run locally (PowerShell)

```powershell
.\venv\Scripts\python.exe -m pip install -r requirements.txt
.\venv\Scripts\python.exe manage.py migrate
.\venv\Scripts\python.exe manage.py createcachetable
.\venv\Scripts\python.exe manage.py runserver
```

Open http://127.0.0.1:8000/.

## Staff portal

```powershell
.\venv\Scripts\python.exe manage.py create_staff support@bouvane.com
```

Open `/accounts/login/`. Verify your email with the emailed code, then add a
passkey or authenticator app. Save the generated recovery codes privately.
Sign in again to complete an actual MFA challenge before entering `/dashboard/`.
Registration is closed; only active staff accounts can use the dashboard.
`/admin/` now redirects to this portal; the Django admin application is removed.

The dashboard supports search, status filters, pagination, enquiry details,
marking enquiries handled, and marking beta signups invited. Status changes are
POST-only, CSRF-protected, and audited. Invited status is a record-keeping action;
it does not send an invitation. Duplicate beta emails are ignored.

The Security page supports passkeys, TOTP, and single-use recovery codes.
Passkeys must use device PIN/biometric verification for passwordless login.
Non-passwordless security keys work as a second factor after a password.
The final enrolled factor cannot be removed until another is added. Email,
password, and active session management are also available in the portal.
Passkeys require HTTPS in production; use `localhost` (not a LAN IP) locally.
Use a stable production hostname: passkeys are bound to their relying-party domain.

Enquiries are saved to SQLite regardless of notification delivery. Optional
contact email notifications use `CONTACT_RECIPIENT` and `DEFAULT_FROM_EMAIL`
environment variables. The default mail backend only prints to the server
console if `EMAIL_HOST` is unset. That mode lets you copy verification codes
from the local server console. Configure SMTP before expecting real delivery.
Beta signups are stored; invitations are not sent automatically.

## Spaceship / Spacemail configuration

Copy `.env.example` to a private environment file and replace the placeholder
secret key and mailbox password. Do not put credentials in source control.
The SMTP server is `mail.spacemail.com`, port `465`, SSL enabled, STARTTLS disabled,
and the username is the full mailbox address (`support@bouvane.com`). See the
[official Spaceship instructions](https://www.spaceship.com/knowledgebase/connect-spacemail-to-email-client/).
Use the mailbox password, not your Spaceship account password.

`support@bouvane.com` is currently the sender, Reply-To, and enquiry destination.
If you create a separate `auth@bouvane.com` mailbox, change `EMAIL_HOST_USER`,
`EMAIL_HOST_PASSWORD`, and `DEFAULT_FROM_EMAIL`; keep `SUPPORT_EMAIL` for replies.

Verification, password reset, account security alerts, MFA alerts, and staff
enquiry notifications are sent as branded HTML with a plain-text alternative.
The logo is included as an inline CID image, not fetched from a third-party
server. Layout uses tables and inline styles for email-client compatibility.
Set `PUBLIC_SITE_URL` to the production HTTPS URL for email footer and staff
enquiry links. Authentication links retain the URLs generated by allauth.
No email is automatically sent to contact-form visitors or beta subscribers.

Configure these variables in your application service. For a local Linux shell,
a private, shell-compatible `.env` can be loaded explicitly with:

```bash
chmod 600 .env
set -a
. ./.env
set +a
```

Production requires `DJANGO_DEBUG=false`, a private `DJANGO_SECRET_KEY` of at
least 50 characters, the correct allowed hosts, HTTPS, and the SMTP values.
Secrets may be generated with `python -c 'import secrets; print(secrets.token_urlsafe(64))'`.
If your TLS terminates at a reverse proxy, configure Django's trusted proxy
headers only for your known proxy so `request.is_secure()` reflects HTTPS.

MFA secrets are encrypted. By default, the encryption key derives from
`DJANGO_SECRET_KEY`; optionally set a dedicated Fernet `MFA_ENCRYPTION_KEY` before
enrollment. Preserve that key securely across deployments. Changing it without
re-encrypting existing data makes existing TOTP/recovery secrets unreadable.
The database cache shares rate limits and TOTP replay protection across workers;
run `createcachetable` once per database.

## Upgrade from the original integer-ID project

Back up `db.sqlite3` and stop all old application workers before applying this
upgrade. Install requirements, load your environment, then run:

```bash
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py createcachetable
python manage.py collectstatic --noinput
```

The migrations assign UUID primary keys to enquiries, beta signups, staff users,
and audit events. Existing enquiry/waitlist data is retained. Legacy `auth_user`
accounts are copied into the new UUID user table with password hashes, staff
flags, group membership, and permissions intact. Each old account must have a
valid, unique email address; migration stops with an actionable error otherwise.
Imported addresses must still be verified. Old sessions are invalidated; old
user tables and old admin logs remain as legacy data, unused by the portal.
Do not run the old application against the upgraded database.

Existing users can sign in with their email and existing password. If you had no
staff user, provision one with `python manage.py create_staff support@bouvane.com`.
The command prompts for a password without echoing it and does not mark the
email verified or skip MFA. No default credentials are created.

## Collect static files for deployment

```bash
python manage.py collectstatic --noinput
```

This collects assets from `static/` and installed apps into `staticfiles/`
(`STATIC_ROOT`). Configure your production web server or hosting platform to
serve `/static/` from that directory. Keep `static/` as the source directory.

This checkout uses development settings. Before a production Django deployment,
configure a private secret key, disable DEBUG, set DJANGO_ALLOWED_HOSTS, serve
collected static files, and configure HTTPS, database backups, and mail delivery.
Google Fonts are optional; local Arial and monospace fallbacks are included.
